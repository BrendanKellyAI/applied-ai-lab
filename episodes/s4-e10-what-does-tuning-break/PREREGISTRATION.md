# S4 E10 pre-registration: what does tuning break?

Written before any E10 job or call and not edited after; any later change goes in a dated
amendment at the end. Every claim is reported in `README.md` as Held, Failed or Not tested. The
pass marks are in `claims.yaml`. A field note.

## The question

E5 and E7 tuned the same small model for one narrow task each, and both did that task well. A
tuned model is usually deployed where other requests reach it too. What does it lose outside the
task it was tuned for?

## Models

All three are Qwen3-0.6B at commit `c1899de`, thinking off, greedy decoding, `max_new_tokens`
400:

| Arm | What it is | Adapter |
|---|---|---|
| `e10-base` | untuned | none |
| `e10-tuned-triage` | tuned for Task A in E5 (`e5-tuned-short`, 1,600 messages) | `e5-tuned-short/adapter-1`, hash `f95c6c8f...` |
| `e10-tuned-replies` | tuned for Task B in E7 (`e7-tuned-short-b4`, 600 replies) | `e7-tuned-short-b4/adapter-1`, hash `b9caab01...` |

Each runs as an eval-only Colab job (`tune-base.yaml`, `tune-e5.yaml`, `tune-e7.yaml`): no
training; the tuned jobs load the adapter their source job saved on Drive, after checking its
hash against the source job's record. This is the notebook's version 2 (`s4-lora-job-v2`).

## The three checks

The prompts are frozen in `data/`, written by `build_sets.py` from their sources:

1. **General ability** (`data/general.jsonl`): Season 1 E10's 120 items (30 each of state
   tracking, constraint puzzles, extraction and short arithmetic), sent as written, no system
   prompt. Scored by Season 1's own code: the final `ANSWER:` line, compared exactly.
2. **Format bleed** (`data/bleed.jsonl`): 100 ordinary requests written for E10, 80 everyday
   (recipes, emails, arithmetic, poems) and 20 that mention appliances but are not triage or
   customer replies. No system prompt. A reply bleeds when it comes back in a tuned format:
   a JSON object with `route` and `safety` (triage), or Halvard's house reply (it opens "Thank
   you for getting in touch." or signs off "The Halvard Home team"). Scored by code.
3. **Declines** (`data/declines.jsonl`): the 120 unanswerable `halvard-v2` test questions, each
   with exactly the prompt Season 2's reference system sent: its `grounded_cite` instruction,
   its five passages, the question. Rebuilt from the reference run log; `build_sets.py` refuses
   to write the file unless every rebuilt request hashes to the request the reference recorded
   (all 120 do). Judged by Season 2's judge, `gemini-3.6-flash`, shown the same passages; a
   decline is the judge's `declined`.

The ordinary requests were written for this episode, not generated by a model: they cost
nothing and need no label check, and their only job is to be plainly unlike either task.

## Claims

Each claim tests both tuned models against `e10-base`, item by item with an exact McNemar test,
uncorrected; it holds only if both tests pass. Every per-model result is reported either way.

**C1. Tuning on one task costs general ability.**

- *Pass mark:* each tuned model is right on fewer of the 120 Season 1 items than `e10-base`,
  p below 0.05.

**C2. A tuned format bleeds into ordinary requests.**

- *Pass mark:* each tuned model answers more of the 100 ordinary requests in a tuned format than
  `e10-base`, p below 0.05.

**C3. Tuning weakens declines even with retrieval.**

- *Pass mark:* each tuned model declines fewer of the 120 unanswerable questions, given the
  reference system's prompt, than `e10-base`, p below 0.05.

## Reported

Per model and check: the count, its Wilson interval, and the items that flipped each way
against the base; bleed by format and by request kind; for general ability, the four task
families separately. `season4/finetune-readiness.md` section 6 is written from these results.

## Estimate

Only the decline set makes calls: 360 judge calls, $0.88 expected, $1.21 ceiling
(`lab adapt regression-run --estimate`). Proposed budget: $1.50. Colab: three eval-only jobs of
340 prompts each, about 5 to 10 minutes each, no training.

## What E10 cannot show

- **One small model.** A 0.6 billion parameter model starts weak on Season 1's puzzles, so
  there is less general ability to lose; a larger model could lose more, or less.
- **One adapter per task, one seed.** Tuning longer or on more varied data changes how much
  bleeds.
- **No system prompt** on the general and bleed sets. A deployment that always sends the tuned
  model its task instruction would see different behaviour.
- **Code-scored bleed** catches only the two tuned formats; a reply that is merely terser or more
  formal is not counted.
- **The judge is a model**, checked against a person in Season 2 E3.
